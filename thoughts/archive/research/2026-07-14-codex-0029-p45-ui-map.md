# codex current-implementation map (pre-spec research)

Scope: `apps/codex` as it stands after 0029 P1–P4 (BUILT). Written to ground a spec for:
(1) 5e.tools-style split-column faceted browse, (2) global header nav w/ categorized dropdowns,
(3) a real landing page, (4) drop the site-wide legacy toggle in favor of always-both search +
an edition facet defaulting to remaster-only, (5) a full bespoke light-parchment restyle
replacing gothic dark theme.

All paths are relative to `apps/codex/` unless prefixed otherwise. Line numbers are best-effort
(gathered via parallel sub-agent reads) — re-confirm exact numbers when writing the spec's cited
lines, since files may have shifted by a few lines since this pass.

## 2. Browse/facet architecture (`src/domain/browse/*`)

### `FilterState` shape — `filterEngine.ts` (~L31-69)
```ts
export interface RangeFilter {
  min?: number;
  max?: number;
  /** Explicitly require the row to carry a value for this facet at all —
   * the ONLY way a range filter excludes a missing-key row (D29-32). */
  hasValue?: boolean;
}
export interface TraitFilter {
  include: ReadonlySet<string>;   // case-folded (lowercase) trait names
  exclude: ReadonlySet<string>;
}
export type SortMode = "name" | "level";
export interface BrowseFilterState {
  query: string;                  // name quick-filter, substring, case-insensitive
  legacy: boolean;                // show `superseded` rows too (site-wide legacy toggle)
  sort: SortMode;
  traits: TraitFilter;
  level: RangeFilter;
  rarity: ReadonlySet<string>;
  sourceBook: ReadonlySet<string>;
  edition: ReadonlySet<string>;   // ordinary multi-select facet, "legacy"|"remaster" values
  facetEnum: ReadonlyMap<string, ReadonlySet<string>>;   // derived facets.* enum widgets
  facetRange: ReadonlyMap<string, RangeFilter>;          // derived facets.* range widgets
}
```
`emptyFilterState()` is the canonical default (`legacy: false`, empty sets/maps).

**Requirement (4) impact**: `legacy: boolean` is the field to delete from `BrowseFilterState`
(replaced by an always-populated `edition` default of `["remaster"]`, see below); `edition:
ReadonlySet<string>` already exists as an ordinary facet and is the natural target for
"defaults to remaster-only."

### Facet definitions — `facetDefs.ts`
- **Not a per-category literal map.** A single flat `Record<string, FacetDef>` keyed on the union
  of every key `src/schema/facetKeys.ts`'s `FACET_KEYS` allowlists per category. `facetKeys.ts`
  owns *which* keys apply to which category (measured coverage/cardinality classifier, D29-32);
  `facetDefs.ts` owns *how* to render/parse/label each key, category-agnostically.
- `allFacetKeys()` computes the union from `FACET_KEYS`; `facetDefs.test.ts` asserts
  `Object.keys(FACET_DEFS)` equals it exactly (conformance gate — will need updating if facet
  keys change under the new browse UI).
- `traits` is deliberately excluded from `facetDefs` — a core, non-facetDefs-routed facet.
- `FacetWidget = "enum" | "tristate" | "range"` — only `"enum"` and `"range"` are actually used by
  any real `FACET_DEFS` entry today; `"tristate"` is reserved (traits' tri-state UI is handled
  entirely outside this map, in `FacetPanel.tsx`'s `TraitsSection` / `filterEngine.ts`'s
  `cycleTraitFilter`/`traitTriState`).
- `FacetDef` interface: `{ key, label, widget, labelMap?, parse?, parseNumeric? }`.
- `FACET_DEFS` covers 21 keys: `actionCost`, `itemCategory`, `size`, `family`, `hp`, `ac`,
  `fortitudeSave`, `reflexSave`, `willSave`, `perception`, `bulk`, `price`, `usage`, `traditions`,
  `castTime`, `range`, `keyAbility`, `trainedSkills`, `valued`, `ancestrySlug`, `speed`.
- Core fns: `facetDefFor(key)`, `enumTagsFor(def, value)`, `numericValueFor(def, value)`,
  `labelFor(def, value)`.

### `src/schema/facetKeys.ts` — the classifier (D29-32/-33)
Doc comment explains the classifier: a candidate key ships when coverage ≥40% of the category's
final entities AND cardinality in the 2..~60 range (soft ceiling, e.g. `equipment.usage` ships at
116 because top-15 values cover 76% of occurrences). Only **15/88 categories** carry any `facets`
key at all (facets populate only on Foundry-merged entities, never `proseOnly`). Per-category
provenance is fully documented in the file's own header comment (feat/creature/equipment/spell/
hazard/weapon/armor/shield/deity/creature-ability/vehicle, etc., each with coverage% and
cardinality). `SPILLOVER_FACET_KEYS` (`featLevel`, `rank`) are banned as exact duplicates of
`level`; `prerequisites` explicitly excluded as free prose.

### `filterEngine.ts` — filtering algorithm
`matchesFilterState(row, state)` short-circuits: legacy/superseded → name query → traits → level →
rarity → source book → edition → derived `facetEnum` → derived `facetRange`.
`applyFilters = rows.filter((row) => matchesFilterState(row, state))`.

**The legacy branch (verbatim)**:
```ts
export function matchesFilterState(row: IndexRow, state: BrowseFilterState): boolean {
  if (!state.legacy && row.superseded) return false;
```
This is **only** about `row.superseded` (see §3 — derived from `remasteredAs.length > 0`, NOT the
`edition` enum). It does not gate on `row.edition` — edition is matched separately at
`if (!matchesEnum([row.edition], state.edition)) return false;`. So **today**: `legacy` toggle =
"show superseded content too" (supersession/currency), while `edition` is an ordinary facet
checkbox list unaffected by the toggle. **Requirement (4) essentially promotes what `edition`
already does (default-select `["remaster"]`) to replace what `legacy` currently does** — but note
these are NOT semantically identical: `superseded` hides content a newer edition replaced;
`edition==="legacy"` hides content that was simply never remastered at all (still current). A spec
must decide whether "edition facet defaults to remaster-only" is meant to subsume the `superseded`
hide-by-default behavior too, since collapsing both into one facet changes what's hidden by
default (today: only superseded rows hidden; tomorrow, if edition defaults to remaster-only, ALL
edition:"legacy" rows are also hidden by default, a strictly larger hidden set).

**Missing-key semantics (D29-32, verbatim comment)**:
```
// ## Missing-key semantics (D29-32, verbatim from the spec)
//
// Entities without a facet key form an implicit "—" bucket:
//   - an ENUM include-selection on that facet drops them (can't match a
//     specific value they don't carry);
//   - a TRAIT exclude-selection never drops them (they trivially don't carry
//     the excluded trait either);
//   - a RANGE filter (min/max) does NOT drop them by default — narrowing a
//     slider "ignores" rows with no value for that key — UNLESS the caller
//     sets `hasValue: true`, an explicit "must carry a value" gate.
```
Other load-bearing helpers: `ambientRows`/`withoutDimension` compute each facet's own option
counts against rows filtered by every *other* active dimension (so selecting an option never
starves sibling counts to 0) — this "faceted-search sibling counting" is exactly the mechanic a
5e.tools-style panel needs, so it's directly reusable. `sortRows` puts level-less rows last on
level sort (never coerces to 0).

### `urlState.ts` — the URL codec
`validateBrowseSearch(raw)` — reads `traits`, `level`, `rarity`, `book`, `edition`, `q`, `legacy`
(boolean-ish), `sort`; then any `f.<facetKeys.ts key>=...` param, dropping unknown facet keys.

**Include/exclude sigil convention** (comment, verbatim):
```
// **Include sigil = NO marker; exclude = `-`** (adversarial B1: a bare `+`
// decodes to a literal space — `URLSearchParams`'s
// `application/x-www-form-urlencoded` convention, and `qss`'s `decode()` is a
// thin wrapper over exactly that — so a `+`-prefixed include marker would be
// silently destroyed before this module ever sees it. No folded trait starts
// with `-` (verified: `foldTrait` only lowercases, the corpus's raw trait
// strings never carry a leading hyphen), so a leading `-` is unambiguous as
// the exclude marker.
```
Implemented in `decodeTraitsParam`/`encodeTraitsParam` (excludes get a `-` prefix before joining).

**Backslash/comma escaping** — `splitCsv`/`escapeCsvToken`/`joinCsv`:
```ts
export function splitCsv(raw: string): string[] {
  const tokens: string[] = [];
  let current = "";
  for (let i = 0; i < raw.length; i++) {
    const ch = raw[i];
    if (ch === "\\" && i + 1 < raw.length) { current += raw[i + 1]; i++; }
    else if (ch === ",") { tokens.push(current); current = ""; }
    else { current += ch; }
  }
  tokens.push(current);
  return tokens;
}
function escapeCsvToken(value: string): string {
  return value.replace(/\\/g, "\\\\").replace(/,/g, "\\,");
}
export function joinCsv(values: readonly string[]): string {
  return values.map(escapeCsvToken).join(",");
}
```
Range params use a `hasValue!` bang-suffix encoding (D29-32 reference in this file is for the
range param, not the missing-key semantics comment itself — that lives in `filterEngine.ts`).
`isCleanSearch(search)` = `Object.keys(search).length === 0` (empty-state-encodes-to-`{}`
invariant — worth preserving so bare category/search URLs stay clean).

### `legacyToggle.ts` — full mechanism (to be REMOVED per requirement 4)
- localStorage key: `"codex:legacy"`.
- **Module-eval-time URL-wins seed** (verbatim):
  ```ts
  if (typeof window !== "undefined") {
    const legacyParam = new URLSearchParams(window.location.search).get("legacy");
    initLegacyToggle(legacyParam === "1" || legacyParam === "true");
  }
  ```
  Rationale (verbatim): "**Why the initial seed happens at MODULE-EVAL time, not a `useEffect`:**
  React fires mount effects bottom-up (children before parents) — so a browse route's OWN 'sync
  the live toggle into my URL' effect could run BEFORE `__root.tsx`'s effect if seeding lived
  there... ES module evaluation has no such ordering hazard."
- `useSyncExternalStore` trio: `getLegacySnapshot()` (module var `current`), `getLegacyServerSnapshot()`
  (always `false`), `subscribeLegacy(listener)` (Set-based pub/sub), `setLegacyToggle(value)`
  (writes storage + broadcasts), `useLegacyToggle()` = `useSyncExternalStore(subscribeLegacy,

- "M4" precedence comment (verbatim): "the URL's `legacy=1` param wins ONLY on the very first
  document load; every subsequent client-side navigation preserves the LIVE toggle... Browse/
  `/search` routes are responsible for reflecting the live value back into their OWN url via a
  search replace... this module only owns the value, never touches the router."
- Exported: `initLegacyToggle`, `getLegacySnapshot`, `getLegacyServerSnapshot`, `subscribeLegacy`,
  `setLegacyToggle`, `useLegacyToggle`, test-only `_resetLegacyToggleForTests()`.

## 3. Legacy/edition data model

### Schema (`src/schema/entity.ts`)
`IndexRow` carries `edition: EditionSchema` (`"remaster" | "legacy"`, ~L56-57) and a **required**
`superseded: z.boolean()` (~L421-434). Derivation in `toIndexRow`:
```ts
superseded: (entity.remasteredAs?.length ?? 0) > 0,
```
File comment (~L414-418, verbatim): "site-wide legacy-toggle predicate, `remasteredAs` non-empty,
NOT `edition === 'legacy'`, which would wrongly hide never-remastered content."

**The distinction, stated precisely**: `edition` is a **display label** baked on at ingest from
AoN/Foundry publication data (a "legacy" entity that was simply never remastered stays
`edition:"legacy"` forever, and is NOT hidden by default today). `superseded` is the **actual
hide/toggle predicate**, derived solely from whether `remasteredAs` is non-empty (i.e. a newer
version exists). A legacy-edition, non-superseded entity (never remastered) is visible by default
today; only entities a newer edition has replaced are hidden by default. **This is the crux fact
for requirement (4)**: switching to "edition facet defaults to remaster-only" will ALSO hide every
still-current, never-remastered legacy-edition entity that today is shown by default — a strictly
larger default-hidden set than the current `superseded`-only behavior. Whether that's the intended
UX (probably yes, given 5e.tools-style sites usually default to "current ruleset only") should be
confirmed but is a real behavior delta worth flagging in the spec, not just a toggle rename.

The `@legacy` id suffix (`CodexId` regex, `entity.ts` ~L48-54) is a **join-time identity
mechanism**, not a display concept: `join.ts` disambiguates a legacy/remaster pair sharing one
`(category,slug)` via `legacy.finalId = \`${preId}@legacy\`` — consumed as a plain crossref/URL
segment elsewhere, never string-matched by the render layer to decide legacy status.

### Category listings / browse
`BrowseListing.tsx` filters `rows.filter((r) => !r.superseded)` when `state.legacy` is off; the
`edition` field renders as a "Remaster"/"Legacy" pill regardless of visibility.

### Search / Omnibar / Pagefind
**Legacy content IS indexed by Pagefind** — `scripts/build-search.ts`'s `buildSearchIndex`
iterates every `IndexRow` in every category with no legacy exclusion, stamping
`filters.superseded = [String(row.superseded)]` and `meta.edition`. Filtering happens at
**query time**, not index time:
```ts
export function supersededFilter(legacy: boolean): string[] | undefined {
  return legacy ? undefined : ["false"];
}
```
`Omnibar.tsx` calls `supersededFilter(legacyRef.current)`; `searchUrlState.ts` does the analogous
thing for `/search` (`if (!state.legacy) out.superseded = ["false"];`). Both surfaces badge results
by the raw `edition` field ("Remaster"/"Legacy"). **Because the index already carries both
`superseded` and `edition` as Pagefind filter facets, "always-both search + an edition facet
defaulting to remaster-only" is a straightforward re-point of the default filter from `superseded`
to `edition` at query time — no reindex needed** (flagged explicitly in the P4 spec's own
host-only-rebuild note — see §8).

### `/rules` tree
Prune predicate `pruneForLegacy` (`treeModel.ts`) is driven off each tree node's own `superseded`
flag, NOT `edition`:
```ts
const selfVisible =
  n.id !== undefined &&
  (n.superseded !== true || (currentId !== undefined && n.id === currentId));
if (selfVisible || children.length > 0) out.push({ ...n, children });
```
`legacyOn === true` short-circuits to a no-op. A whole book that prunes to empty (e.g. Dark
Archive, Guns & Gears — 100% superseded) renders a collapsed "all N hidden" header instead of
disappearing (`RulesTree.tsx`: `allHidden = !legacy && legacyPruned.length === 0 &&
book.hiddenWhenLegacyOff > 0`). Per-book edition/license pills show unconditionally at the header,
independent of the toggle.

### Attached sidebars
`AttachedSidebars.tsx` filters on the same `superseded` boolean:
```ts
const visible = legacy ? sidebars : sidebars.filter((s) => !s.superseded);
const hiddenCount = sidebars.length - visible.length;
```
Reuses RulesTree's "N hidden" note class; a still-visible superseded sidebar gets an inline
`Legacy` `codex-edition-pill`.

### Entity detail pages
Entity pages render **regardless of the legacy toggle** (comments confirm "only listings/sidebars
hide superseded content"). Always shows an `EditionPill` (raw `entity.edition` enum) plus an
`EditionBanner` that inspects `remasteredAs`/`legacyOf` directly:
```ts
if (entity.remasteredAs !== undefined && entity.remasteredAs.length > 0) { /* "This is the legacy version." */ }
if (entity.legacyOf !== undefined && entity.legacyOf.length > 0) { /* "(legacy version)" */ }
```
This layer is edition-neutral and needs no change for requirement (4) — entity pages already
always show both editions' relationship regardless of any listing-level default.

### Inheritance from `@astra/gothic`
`globals.css` has no `@import` itself — the import happens at `__root.tsx` (`import
"@astra/gothic/theme.css"`, immediately before `import "@/styles/globals.css"`, so gothic's
cascade layers load first). `globals.css`'s own header comment states this explicitly.

`libs/ts/gothic/src/theme.css` provides:
- `@import "tailwindcss"` + `@source "./"` (forces Tailwind to scan gothic's own component source).
- Bundled `@font-face` for "Caslon Antique" (body) / "ITC Serif Gothic" (display) from `/fonts/`.
- An `@theme {...}` block defining ~20 tokens under Tailwind's `--color-*`/`--font-*` namespace:

  `--color-redaction`) — **this parchment palette already exists in gothic and is used by the
  "diegetic" content mode** (`[data-mode="diegetic"]` overrides in gothic's own `@layer
  components`) — worth investigating as a possible starting point/precedent for the bespoke
  parchment restyle rather than inventing tokens from scratch, though it's currently scoped to
  content-mode styling, not a whole-site light theme.
- Three font families + motion tokens (`--ease-out`, `--duration-fast/base/slow`).
- `@layer components {...}` block: `.gothic-card`, `.gothic-content`, `.gothic-prose`,

  vellum bodies; codex's own `codex-*` classes are separate hand-authored structural classes that
  just consume the same token vars.
- Per-player/host `--identity-color` explicitly NOT here (comes from `ontology-being` at runtime).

### Dark-only theme mechanism
No theme *switching* exists — dark-only, pre-hydration-forced, no `prefers-color-scheme`, no real
`data-theme` branch. Mechanism = the `__root.tsx` inline script (§1) stamping
`saved-theme="dark"` on `<html>` before hydration, purely to make the pre-hydration/hydration
attribute mismatch predictable (not read anywhere else — grep confirms `saved-theme`/`data-theme`
has no other consumer in codex; the only theme-*adjacent* localStorage keys in the app are
`codex:legacy` (legacyToggle) and the rules-tree collapse-state key (`RulesTree.tsx`), neither
color-related).

### Blast radius / what dropping gothic entirely requires
- Delete `import "@astra/gothic/theme.css"` at `__root.tsx` (1 line) — but this is the ONLY source
  of every `--color-*`/`--font-*` token `globals.css` uses throughout its ~1,017 lines, so **all of
  them must be redefined locally** (a new light-parchment token set) before removing the import,
  or `globals.css` renders unstyled/black-on-black.
- Replace every literal `gothic-card*`/`gothic-content`/`gothic-prose`/`gothic-columns` className
  usage (5 files: `nodes.tsx`, `statblock.tsx`, `entityPage.tsx`) with new bespoke classes/styles.
- Replace or re-skin every gothic **component** import (not just CSS): `TraitPill` (`traits.tsx`),
  `ActionGlyph`+`normalizeActionCost`+`ActionCost` type (`actionGlyph.tsx`), `ErrorChip` (`nodes.tsx`),
  `Input` (`RulesTree.tsx`, likely `FacetPanel.tsx`), `Button` (`EmptyState.tsx`). These are React
  components, not just CSS classes — a full de-gothic requires either forking/reimplementing them
  in codex or keeping a thin re-skinned wrapper.
- No suspicious dark-assuming literal colors found outside the token system — `html`/`body`
  background/text are set unconditionally via `var(--color-void)`/`var(--color-ink)`, so a
  values-only token swap (new light-parchment `--color-*` values under the same names) is
  plausible IF gothic's own components (TraitPill, ActionGlyph, Input, Button, ErrorChip) also
  read the same token vars rather than hardcoding dark-mode colors internally — **verify gothic's
  own component source before assuming a token-swap-only restyle is sufficient**; this map only
  covers codex's own files, not gothic's component internals.

### Category taxonomy/grouping (`categoryGroup.ts`)
Confirmed: **rule-based, not a literal 88-entry list.**
```ts
export type CategoryGroup = "creature" | "hazard" | "spell" | "equipment" | "feat" | "generic";
const EQUIPMENT_CATEGORIES = new Set(["weapon","armor","shield","equipment","consumable","treasure"]);
export function categoryGroupOf(category: string): CategoryGroup {
  if (category === "creature") return "creature";
  if (category === "hazard") return "hazard";
  if (category === "spell") return "spell";
  if (category === "feat") return "feat";
  if (EQUIPMENT_CATEGORIES.has(category)) return "equipment";
  return "generic";
}
```
So only **9 categories** get a named group (creature, hazard, spell, feat + the 6-member equipment
set — note `equipment` itself is both a category name and the group name); the remaining ~79 of
the corpus's **88 total categories** (confirmed via `data/corpus/` directory count = 93 dirs incl.
non-category housekeeping; `report.ts` comment says "73/88 categories carry no facets at all")
fall into the catch-all `"generic"` group. **A "global header nav with categorized dropdowns"
(requirement 2) will need a materially richer taxonomy than this 6-bucket render-shape grouping**
— this file answers "how do I lay out THIS entity's page" not "how should the nav organize 88
categories for browsing," so a new nav taxonomy is very likely net-new, though `categoryGroup.ts`'s
5 named buckets could seed the "big" nav sections.

**Hydration seams to preserve or deliberately simplify (not silently drop):**
- The M4 two-phase `hasHydrated ? liveLegacy : search.legacy === true` pattern in
  `$category/index.tsx`, `$category/$slug.tsx`, `rules.tsx` — **collapses to a plain URL-only read
  once the site-wide legacy toggle is removed** (no more second live-toggle source of truth to
  race against SSR). This is a simplification, not something to "preserve," but the spec should
  say so explicitly rather than leave a dangling half-removed pattern.
- The two `suppressHydrationWarning` occurrences (`__root.tsx` `<html>`/`<body>`) exist SOLELY to
  paper over the dark-theme pre-hydration script's attribute stamp — if the restyle removes the
  forced dark-only script (e.g. because parchment IS the only theme, no attribute stamping
  needed), these `suppressHydrationWarning` props and the script both likely disappear together.
  If the new design instead needs its OWN pre-hydration script (e.g. a print-vs-screen mode toggle,
  or restoring a persisted reader preference), the same `suppressHydrationWarning` pattern will
  need to be re-applied at whatever DOM node the new script stamps.
- `legacyToggle.ts`'s module-eval-time URL-wins seeding pattern (ES-module-evaluation-order trick
  to beat React's bottom-up effect firing) is a reusable idiom worth keeping in mind if the new
  edition-facet-default needs an analogous "URL wins on first load, then live state after" seed —
  though per §3, if edition simply always defaults to `["remaster"]` server-side with no
  site-wide override to persist, this whole class of hydration-race problem may not recur at all.

**Telemetry wiring** (`src/observe/rum.ts`, `rumConfig.ts`): `rum.ts` is a thin client-only caller
over `@astra/site-kit/web`'s `startRumKit`, invoked from `__root.tsx`'s `useEffect` + dynamic
import (keeps the browser OTel Web SDK out of the SSR bundle). `rumConfig.ts` is a `createServerFn`
(`getRumConfig`) reading `cfg.telemetry.rumEndpoint` + deriving `${cfg.codex.serviceName}-rum` from
`loadConfig()` (config-single-source). Together: **client-side RUM only**; SSR-side traces/logs/
metrics come from `createSsrServer`'s own `initTelemetry("astra.codex")` call. Any header/landing-
page rework must keep the RUM effect mounted in the (possibly restructured) root shell.

## Biggest rework couplings/risks (see executive summary for the distilled version)

1. Removing the legacy toggle touches 7 files (routes ×4, `Omnibar.tsx`, `SearchPage.tsx`,
   `RulesLayout.tsx`) plus 4 hide-by-default call sites (`filterEngine.ts`, `pagefindClient.ts`/
   `searchUrlState.ts`, `treeModel.ts`, `AttachedSidebars.tsx`) — but `BrowseListing.tsx`/
   `FacetPanel.tsx` need ZERO changes since they never imported `legacyToggle` directly, and the
   `edition` facet UI already exists.
2. `superseded` (hide-by-default today) and `edition==="legacy"` (the new default-hide criterion)
   are NOT the same set — the new default will hide strictly more content (never-remastered
   legacy-only entities too) than today's toggle. Worth a stakeholder confirmation, not just an
   implementation detail.
3. Dropping gothic isn't just deleting a CSS import — 6+ React components (`TraitPill`,
   `ActionGlyph`, `Input`, `Button`, `ErrorChip`, plus gothic's markdown-body classes) are imported
   directly and would need reimplementation or re-skinning, and `globals.css`'s ~1,017 lines
   consume gothic's tokens exclusively (zero tokens of its own) — the entire visual system inherits
   from one 1-line import.
4. `render/goldens.test.tsx` is byte-exact HTML — guaranteed full regeneration under any restyle.
   `ssrSmoke.test.ts` (550 lines) is the broadest blast-radius test for routing/shell changes.
5. `categoryGroup.ts`'s 6-bucket grouping is a render-shape concern (which page layout to use), not
   a browsing taxonomy — a real categorized nav (req. 2) is largely net-new information
   architecture over 88 categories, not a repurposing of existing code.
6. SSR weight budgets (393 KB/78 KB gz `/rules`, 697 KB/64 KB gz `/sources`, 378 KB/78 KB gz
   heaviest sidebar host) are the pre-rework baseline to re-measure, not exceed silently.
